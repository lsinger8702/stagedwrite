## 迁移契约

schema 1–4 的既有列保持不变，升级只新增表／索引。CREATE TABLE IF NOT EXISTS 仅在这一前提下足够。
启动在提升版本之前核查必需列，缺列报 STORAGE_SCHEMA_MISMATCH 并回滚版本更新。
此检查不验证所有约束、索引、列类型或数据内容；数据库仍是可信内部状态，不提供任意损坏库修复。
今后变更既有列必须加入明确的数据迁移，再更新版本，不能只扩大版本接受列表。

现有 v1 布局测试之外，新增真实 v2/v3 表布局 fixture：包含草稿、固定计划、检查及未知 run。
升级后原回执、发布封存与凭据仍有效；v2 缺失会话证据继续拒绝接管，v3 已释放会话可接管并核对。
不使用“当前库改版本号”替代历史布局验收；另测缺列时版本不被错误提升。

## 干净消费者验收

运行 `npm run verify:package`：

1. 构建并 npm pack 到临时目录，检查运行入口及声明存在，测试和示例没有混入 tarball。
2. 临时目录通过 npm install 安装 tarball 与实际依赖，禁用依赖脚本；不做 npm link。
3. 通过包名导入，创建、预检、关闭、重开后发布，再重开读取 SQLite run。
4. 在消费者目录编译公共 TypeScript API 的引用。编译器来自开发仓库，但包和依赖从消费者目录解析。
5. 删除临时文件，输出版本、压缩包大小与检查项。

这验证独立安装消费，不是外部用户体验反馈；安装需要访问 npm registry 或可用缓存。
GitHub CI 从全新 checkout 执行 npm ci、全部测试、离线示例及打包消费者验收。
不运行真实服务示例，不发布包。依赖解析未锁定未来所有版本，支持范围以每次 CI 结果为准。

## 旧 API 去留决定

0.0.1 及计划中的 0.1.0 保留 deprecated `StagedWrite` 导出，以兼容现有原型示例和回归测试。
新文档和新能力统一使用 `createStagedWrite`；不再给旧标量入口增加图存储、恢复或导入功能。
两者共用 ExecutionRuntime，但草稿与预检入口不同。旧入口的 rule 异常会裸抛并作废旧证书；这是已知差异。

从旧入口迁移：注册单节点 definition，使用 node.add 创建节点，把顶层 set/remove/reset 改为带 nodeId 的图 OP；
将 adapter.plan 改为读取 GraphDraft，把执行函数装配到有稳定 ID/version/target 的 GraphExecutor。
需要持久化时只能使用图入口。首次公开发布前不直接删除旧导出；将来删除需版本说明和示例迁移。
