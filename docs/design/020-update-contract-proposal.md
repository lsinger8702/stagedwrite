# 020：固定图 update 契约与状态矩阵

**状态：U0 契约已批准，2026-09-16。项目所有者明确回复“同意”。000 已同步批准边界，018 仍记录当前实现。本文不表示运行时已支持 update；数据模型设计见 [021](021-update-data-model.md)。**

**建议核心：同一个 Draft 保留资源身份；一次全量成功后可接受新意图、新建 update Run；任何未解决 Run 都必须先 resume。diff 不能证明在途请求已经结束。**

## 1. 范围与分工

首版仅更新固定节点、固定边、固定远端 ID 的可变标量字段。一次节点更新仍至多一个远端写步骤。新增、删除、替换节点、修改关系、跨目标、复合远端效果、rollback、自动放弃均不开放。不可原地修改的字段给出具体诊断，不偷偷转换成 create。

库负责版本、归属、租约、检查凭据、逐步事实、成功基线和修复保护。接入方负责业务值到受管远端字段的投影、读取与归一化、字段可写性/清空语义、真实请求和效果查证。不能通过通用 JSON diff 推断任意远端请求；不引入双向路由框架。执行器应显式声明 update 能力；没有该能力的现有接入仍拒绝成功后的 edit。

update 的对比记录需要：受管字段、可比较的规范值、对应图路径、期望写入/清空、远端 ID、可用的条件写令牌。接口类型由 U1 落实，但不得把缺失值、未知读取和 null 合并。字段映射是否正确仍需 adapter 测试证明。

## 2. 四类状态不要合成一列

| 对象 | 表达什么 | 不表达什么 |
|---|---|---|
| Draft.status：pending / published | 当前意图是否已全量确认发布 | 远端现在是否无漂移、是否存在活 worker |
| publishedArtifactId | 最近全量成功意图，reset 的固定基线 | 最近每一个局部副作用 |
| currentRunId + Run.state | 当前/最后执行归属；running / blocked / unknown / published | 分布式锁 |
| Binding + Attempt/确认事实 | 远端身份、逐次已确认与未知效果 | 仅凭缺记录就证明远端不存在 |

已发布 Draft 每次成功 edit 都变为 pending、旧检查失效，即使净意图未变；版本只做 CAS。必须经新的 preflight/publish 确认，不能靠 hash 自动恢复 published。published 是历史确认，不保证没有外部漂移；preflight 发现 drift 返回阻断诊断，不把只读检查变成隐式回滚发布状态。

initialSnapshot 永久不变。只有全图成功提交才能推进 publishedArtifactId；部分成功不改变 reset 基线。lastPublishedAt 记录成功提交时间，重复观察不刷新。currentRunId 完成后仍保留，新 Run 认领时原子替换，历史 Run 不删除。

## 3. 发布分派矩阵（按顺序判定）

以下操作都先验证 Draft/目标身份和有效租约；表中的检查是事务内判定，不是锁外查后写。

| 编号 | 情形 | 行为 | 新 Run / 远端写 |
|---|---|---|---|
| P01 | 相同 certificate 已被某次发布采用 | 返回该次提交/Run 的历史结果，同时标明当前版本/当前 Run | 无 / 无 |
| P02 | currentRun 未完成，调用 publish | 返回当前 Run 与 resume 提示；不采用新 certificate。显式不同 runId 拒绝 | 无 / 无 |
| P03 | 没有历史成功也没有 Run | 有效预检后认领 initial_create | 一个 / 按计划 |
| P04 | 无历史成功但存在失败 initial_create，编辑了新版本 | 仍走 P02；使用 resume | 无 / 无 |
| P05 | 有历史成功、无未决 Run，但凭据过期或不属于当前版本 | 要求重新 preflight | 无 / 无 |
| P06 | 有历史成功、有效新检查、有字段差异 | 认领 update，绑定原远端 ID | 一个 / 按计划 |
| P07 | 有历史成功、有效新检查、全图无差异 | 原子记录无写入发布提交并推进当前成功意图 | 无 / 无 |
| P08 | 同时两次 publish，使用相同或不同检查凭据 | 锁争用者 busy；获得锁后重新判定，不能凭锁外结果创建第二 Run | 至多一个 / 不重复派发 |
| P09 | 明确指定 runId 已被其他提交或 Draft 使用 | 身份冲突；不能把 ID 当更新入口 | 无 / 无 |
| P10 | target、注册定义/执行器版本绑定不匹配 | 阻断；不能靠新 Run 绕过绑定 | 无 / 无 |

P01 只允许重放已落库的采用记录，不能重放任意旧 passed 检查。响应必须区分“历史提交已完成”和“当前 Draft 已发布”，避免旧证书的成功响应被当作新意图成功。P01 的显式 runId 必须与原采用记录一致。

**无差异提交建议不建执行 Run，但必须有持久采用记录。** 以 certificate/Artifact 身份记录：draftId、version、kind=noop、成功 Artifact、提交时间与 runId=null；与推进成功基线同事务。重复调用返回同记录。不要伪造 applied Attempt 或把上次 Run 的成功充作本次执行。显式提供 runId 的 no-op 请求拒绝并说明无需执行 Run，不能静默忽略调用者 ID。精确响应字段由 U1 定稿。

这是对 019 中 no-op 开放问题的明确建议：少建空 Run，但增加最小提交事实；若不接受该额外记录，可讨论统一空 Run，不能只改 status 而没有重放依据。

## 4. edit / reset / resume 矩阵

| 编号 | 情形 | 处理 |
|---|---|---|
| E01 | 首次认领前 | 沿用现有图编辑能力 |
| E02 | 全量成功后新 edit | update 能力存在才允许；只改字段；保留全部 Binding 与旧成功基线 |
| E03 | 本次 Run 未完成，编辑未成功节点 | 允许字段修复；不切 Run；下一次 resume 采用修订 |
| E04 | 本次 Run 已成功节点，含 planner 未使用的字段 | 拒绝改整个节点的意图；旧 Run 的成功不永久封锁新 Run |
| E05 | unknown 节点被编辑 | 可保存修复意图，但不能发送；先查证旧请求 |
| E06 | reset | 恢复最近全量成功声明；首次成功前恢复 initialSnapshot；仍受 E04 保护 |
| E07 | 失败 update 中想 reset 全图 | 若会修改本 Run 已成功节点，全批拒绝；不能把 reset 当补偿 |
| E08 | edit 与执行并发 | 同一 Draft 租约串行；CAS 不符拒绝，不自动重放 OP |
| R01 | resume 当前未完成 Run，无 unknown | 重新检查当前目标与远端事实，验证保护后继续；update 即使版本未变也不能沿用旧远端观察直接写 |
| R02 | resume 存在 pending/unknown Attempt | 先按旧输入、旧 key、旧远端 ID 查证；未解决则返回 unknown |
| R03 | 查证 applied，当前意图与回执冲突 | 立即保存事实，阻断矛盾修订；用户需恢复该节点为已确认意图 |
| R04 | 查证 no_effect | 必须证明旧请求不会以后生效；才可重新检查并采用修复 |
| R05 | 当前未完成节点修复后无需写入 | 有确切无在途请求证据才可标记无写入完成；不伪造远端回执 |
| R06 | resume 历史已完成 Run | 仅观察该历史 Run；不推进当前 Draft、不刷新基线 |
| R07 | 非当前 Run 却显示未完成 | 存储不变量损坏，拒绝推进；不自动抢占 currentRunId |

为保持步骤身份稳定，update 计划对固定节点保存稳定槽位，槽位动作是 update 或 noop。未完成槽位在修订时可在二者间切换；本 Run 已确认完成的节点受完整意图保护。步骤依赖/顺序仍固定；没有 HTTP 的槽位记录“无需写入”的检查证据，不记 applied 请求。先查证全体旧未知尝试，再处理任何新写入。

**这个保守方案确实有代价：部分成功后不能任意改成功节点；永久 blocked/unknown 也不能另开 Run。** 本轮没有 abandon/人工裁决出口。解决它需要独立的终止/效果归属契约，不能以“update 通常幂等”跳过。

## 5. diff / drift 完整判定域

对每个可比较、受管字段：B=最后确认的远端规范值，D=当前声明投影的目标值，O=本轮远端观察。B 不是无条件取上次全图 Artifact：本 Run 局部成功已更新节点确认事实。

以下五行穷尽 B、D、O 的相等关系（前提是三者均已知）：

| 编号 | 关系 | 结果 |
|---|---|---|
| F01 | B=D=O | noop |
| F02 | B=O，D 不同 | update |
| F03 | B=D，O 不同 | drift，阻断；不能悄悄改回 |
| F04 | D=O，B 不同 | 目标已满足，可作为本轮无需写入的观察证据；不是某次旧请求的成功证据 |
| F05 | 三者各不相同 | 用户修改与远端修改冲突，阻断 |

前置异常与三态：

| 编号 | 情形 | 结果 |
|---|---|---|
| F06 | 任意相关旧请求未决 | 优先 R02；即使 D=O 也不得推断旧请求已结束 |
| F07 | 远端读取超时/权限不足/归一化失败 | pending/incomplete 或具体阻断诊断；无发布资格 |
| F08 | Binding 缺失/远端对象不存在/身份不符 | 阻断；update 不自动补建 |
| F09 | B 缺少可比较证据 | 阻断并提示接入能力缺失；不能拿当前 O 冒充历史 B |
| F10 | set / remove | 分别编译为明确目标值/明确清空；不支持则诊断 |
| F11 | reset | 先恢复固定基线的声明，再按 F01–F10 判定 |
| F12 | 声明缺席 | 不表示清空，不发送该字段；不能自动接管/忘掉此前受管事实，受管范围变化需明确契约，本版拒绝隐式变化 |
| F13 | 非受管字段变化 | 不自动写回，不纳入自动收敛承诺 |

F03/F05 不提供自动覆盖模式。返回图路径、message、期望/观察差异与可选建议，交由调用方判断。候选 OP 不能解除 unknown 或绕过效果证据。

reset 基线中的未声明、明确 remove、set null 必须保留区别。首次创建产生的服务端默认值不能写回作者声明；可单独记录为远端事实。旧实验数据没有规范确认值时不得猜测补全，数据处理方式在 U1 明确。

## 6. 时间、并发与失败窗口

| 编号 | 窗口 | 要求 |
|---|---|---|
| C01 | 检查期间 edit、确认事实变化、另一轮检查开始 | version/checkEpoch/resourceRevision 不符使结果失效 |
| C02 | preflight 通过后远端改变 | 写前重新读取/验证前置条件；有变化就返回需重新预检，不能静默执行另一个计划 |
| C03 | 写前读取后又被其他系统修改 | 远端支持 CAS 则条件写；否则首版只承诺单一写入方假设下工作，Draft 锁不提供跨系统排他 |
| C04 | 租约失效/进程退出，Attempt 已保存 | 不证明无效果；新执行者先查证原请求 |
| C05 | 远端成功但回执存储失败 | 保留 pending/unknown；迟到事实必须核对 Run/step/key/attempt 后由合法持锁者采纳 |
| C06 | 旧 Run 迟到或重复回执 | 仅关联原尝试；不得覆盖新 Run 的最新事实/成功基线；矛盾证据阻断 |
| C07 | 最后一步成功、整图提交前退出 | 持久逐步事实后 resume 完成原子收尾；不重发成功步骤 |
| C08 | 整图提交成功但响应丢失 | 重复 certificate / resume 返回已提交结果 |
| C09 | A→B 成功，再意图改回 A | 新 update 合法；不能因为 A 的 hash 历史出现过而永久排重 |
| C10 | 相同版本、重复预检产生不同 Artifact | 单次采用原子认领；无未决 Run 才考虑新的无差异提交，不按 Artifact 数量发写请求 |

事务内不能执行网络 I/O。持锁获取观察 → 事务验证本地归属并保存 Attempt → 网络调用 → 事务保存效果。远端条件写令牌及本次观察进入原请求证据。单一写入方是接入限制，不是库能证明的保证。

尤其是 update 查证：读取到值 B 不能证明先前 A→B 的请求结束；请求仍可能排队，并在之后 B→C 后重新写回 B。adapter 的 applied 证据必须足以确认该原尝试终结，no_effect 必须排除迟到生效。没有能力就保持 unknown。create 样例基于对象身份的查证不能不经验证直接用于 update。

## 7. 存储和实现影响（只定位，不改代码）

- `src/managed/types.ts`：Run.kind 扩展、规范观察/确认事实、noop 完成证据、发布采用记录；Binding 身份不变，最新事实与原创建回执分开。
- `src/managed/engine.ts`：当前 publish 只要有 currentRunId 就观察；应按第 3 节分派。当前成功 edit 直接拒绝；需按第 4 节保护。当前 resume 仅版本变化才重检；update 必须增加新鲜远端检查。
- 当前每节点恰好 create 步骤和只以 applied 完成的假设，须改为稳定槽位与明确 noop 完成，不能把未执行伪装成已写入。
- 当前 `lastPublishedAt ??=` 只记录第一次成功；目标行为每次新成功提交更新。重复调用不刷新。
- Store 的“一 Draft 至多一个 Run”改成“一 Draft 至多一个未解决 Run，首次创建 Run 至多一个”。换指针、创建 Run/记录采用、保存成功基线均需原子性。
- 不强制新增 Draft 业务列，不用 version/hash 充当锁。新增事实放在 Artifact/Run/存储元数据，具体布局交 U1。
