# 000：项目原则与设计变更约束

**置顶原则：后续开发遇到与本文件已明确原则的冲突，必须先与项目所有者讨论，取得其对具体变更的明确同意，再修改方案和实现。不得用已有代码、旧文档、评审建议或“更通用”的实现替代这一步。**

**当前结论：Draft / publish / resume 的核心语义已明确。本轮按“先做后看”的要求实现了可评阅的多 Run 接口；其参数选择不是新增的不可变原则，外部存储接入、MID 等仍未决。不要混淆实现选择与已明确原则。**

状态：2026-09-14，依据项目所有者在本次讨论中明确的意图整理。下列“已明确原则”和“未决设计”分开管理。本文是设计主线；阶段实现记录和历史测试不覆盖本文。项目所有者后续的明确指示可以变更原则，需同步记录具体决定。

## 已明确原则

### P1：库的定位与图模型

**StagedWrite 是围绕图式工作意图、三态 OP、面向 LLM 的预检及执行闭环的可嵌入库。Draft 以图建模，单节点也是图；节点与关系显式描述。不得自行改成任意嵌套 JSON 或通用工作流引擎来替代这条主线。**

节点 schema 的复用引用、图中节点关系、执行后的远端引用是不同概念，不能混用身份。业务对象图也不等同于执行依赖图。

### P2：意图与三态 OP

**set 表达显式值，remove 表达显式清空，reset 撤回声明；未声明、清空和显式 null 不能合并。规则或编译不得静默替用户决定意图。**

**创建 Draft 应携带调用方的初始图意图，创建成功即含工作内容；schema 只约束结构，不能代替或猜测本次意图。业务问题可由后续预检指出，不要求创建时已可发布。**

缺发布必填内容可以作为未完成 Draft 保存，已提供内容须符合结构约束。编辑通过原子 OP 批次与版本检查进行。

### P3：Preflight 服务于具体诊断与修复决策

**Preflight 必须返回被检查版本的 Draft preview 和实际问题诊断；message 是核心，必须尽量解释当前哪里错、为什么错。不能只把规则目录交给 LLM 自行寻找错误。**

**规则可以给提示、候选值、候选值附带的 repair OP 数组、多组候选修复与关联位置；这些都是可选信息，不要求注册固定 resolution，也不禁止建议 OP。调用方或 LLM 根据 preview、诊断和用户意图选择、修改或生成 OP，库校验应用后重新预检。**

**异步检查可以返回 pending，由上游再次调用 preflight；任务和进度可由接入方维护，不要求库自建调度系统。pending 不等于通过，仍需返回当前预览和已获得的诊断。**

检查失败也需要当前 Draft 预览。preview 不是远端请求体或已执行结果。规则异常属于检查未完成，不伪装成业务字段错误或检查通过。已实现契约见 [004](004-graph-preflight.md)。

### P4：Draft 与执行事实分开

**Draft 承接工作内容和用户意图，不承担密钥管理或执行进度。Run 表示某一次执行及其事实；Draft 的身份与 Run 的身份不能因为内容相同就合并。**

这里统一使用 Draft 指工作内容、Run 指一次执行，避免沿用旧代码对象名称造成歧义。Draft 可只保留最新工作内容，不要求做 Git 式版本历史。编辑版本用于并发检查；Run 需要保留恢复该次执行所需的输入/计划与事实，它们不是 Draft 的 Git 历史。

### P5：Publish 与 Resume 的主语义

**一次新的逻辑 publish 表达一次新的执行意图，建立独立 Run；同一 Draft、同样内容再次表达新 publish 意图，也应能产生另一次执行。不能用 draftId 或内容摘要自动合并两次独立意图。**

**只要一次 publish 尚未全部成功，调用方要继续完成该次执行，就使用 resume；进程故障或重启不是前提。resume 针对已有 Run，继续该次执行；允许基于 publish/resume 诊断 edit Draft 后更新尚未生效部分的输入与计划。保留成功事实、历史请求和原 Run 身份；未知请求先查证，不能被新输入覆盖。**

用户再次发布与同一提交因通信失败而重传是两件事，区分意图由上游表达。本轮实现以可选 runId 表达提交身份，详见 006；长期是否拆分 requestId 留待评阅。新 Run 表达独立执行，不代表每个平台都必然创建一个新资源；业务请求的效果由适配器决定。

### P6：恢复依赖执行事实

**恢复不能丢弃已确认成功的效果，也不能把未知结果当成未执行。同一个 Run 的重试必须保持原请求关联身份；runId 只是定位符，本身不是执行进度。**

恢复所需事实必须能够被取回，包括固定计划、步骤状态、原请求身份和已知结果。它们放在哪个存储、由谁提供存取接口，尚未定稿；不能因此把进度塞回 Draft，或直接根据一个游标捏造成功记录。

### P7：Rollback 与后续编辑的范围

**resume 与 rollback 都以某一次 Run 为语义对象：前者继续执行，后者补偿已产生的效果。业务资源的补偿行为由接入方定义，不能由库猜测通用删除方式。**

补偿是 Saga 语义，不承诺数学上的完全逆操作。具体补偿注册、顺序、失败重试与公共 API 尚未设计；本轮不要求实现 rollback。

**未完成执行的诊断修复属于当前闭环：publish/resume 返回可选诊断，调用方或 LLM 生成三态 OP，edit 后 resume 同一 Run。全部成功之后的远端资源编辑与 drift 仍可延后。**

这不要求现在就实现完整远端编辑，也不授权移除恢复保护来提前开放编辑。

## 未决设计：不得标为定稿

| 问题 | 已明确边界 | 待讨论内容 |
|---|---|---|
| 新执行身份 | 新意图与恢复旧意图区分 | 本轮采用可选上游 runId，同 ID 同提交只观察；省略则新 UUID，供用户评阅 |
| 执行记录接入 | 恢复需要执行事实，事实不属于 Draft 内容 | 内置 Store、可插拔 Store、调用方提交检查点，或组合；一致性责任与最小协议 |
| 指定恢复位置 | 不能把起点参数当成已执行证据 | 是否提供 startAt；若提供，怎样验证与已确认事实一致 |
| MID | 不得混同图节点 ID、Run ID 和远端 ID | MID 在本项目准确指什么、生命周期和命名；尚未正式定义 |
| 状态保留 | 保留恢复所需事实 | 是否对外承诺每一次状态变更的完整事件历史、查询接口与保留策略 |
| 多 Run 生命周期 | 同一 Draft 支持独立发布意图 | 本轮已实现独立并发、每 Run 快照和 schema 5 迁移；发布后 edit 延期 |
| 编译扩展 | 图意图与真实请求体不是一回事 | 编译产物与适配器接口如何长期划分，不在本次偷偷确定 |

当前 SQLite 与内存模式继续保留。项目所有者随后要求先实现并查看真实输入输出，本轮据此选择最小提交身份与每 Run 输入存储方案，不改变已有恢复保护。其余未决扩展不能因本轮实现获得自动批准。

## 原则冲突处理流程

**发现冲突时，暂停依赖该选择的修改；明确列出冲突原则编号、当前行为、拟改行为、理由及影响，与项目所有者讨论。没有明确同意，不修改原则，也不通过代码、测试、默认参数或文档重命名间接改变它。**

不受冲突影响的工作可以继续。旧实现与目标不同应标记为待对齐，不能为了让文档与旧代码一致而撤销目标。外部评审意见是分析材料，不自动获得原则变更授权。

得到明确同意后，先在下方记录决定，再同步功能设计、范围、实现、示例和测试；保留旧决定被替代的说明。普通实现细节在既定原则内可自主处理，不需要对每个细节重新申请确认。
