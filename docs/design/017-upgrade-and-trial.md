## 升级前应明确的区别

| 来源 | 数据迁移后 | 原执行恢复 |
|---|---|---|
| schema 1 | 保留草稿，创建当前表结构 | 旧版本没有执行记录表 |
| schema 2 | 草稿、计划、run、回执仍可读取；保留发布封存 | 没有 session 证据的未完成 run 不可通过新引擎接管 |
| schema 3 | 保留会话和执行事实，升级至 4 | 旧 owner 已释放或同主机进程已退出时可显式 recover |
| schema 4 | 同版本打开，检查必要列 | 按既有 owner 和证据条件恢复 |

schema 2 的限制包括 recover、resume、adjudicate、stopRetry，不能靠一个新命令补造旧 owner 证据。
终态失败仍可按既有条件派生，确认回执可按 importConfirmed 的终态／映射约束接入独立工作。
在途 run 没有被自动标成 failed 或 closed，也不能用 importConfirmed 绕过终态限制。

如果原兼容进程仍在，应先在原环境完成或解决在途工作，再升级。若原进程已丢失，保留旧数据库和原请求证据，
由实际系统的核对／处置流程确认远端结果；当前库不提供迁移后强制推进这条旧 run 的入口。
不能把“库打不开恢复入口”解释为“远端没有效果”，更不能自动新建相同请求。

升级前保留一致性备份：停止全部访问者并正常关闭连接后再复制数据库；若仍有 WAL，不能仅复制主文件当作完整备份。
恢复旧备份可能漏掉备份后已经生效的远端操作，不能盲目继续派发；数据库备份不回滚远端。
旧二进制拒绝 schema 4。当前不提供向旧格式降级的转换工具，不建议手工修改版本号、owner 或 session 绕过检查。

## 外部试用步骤

由未参与实现的开发者在自己的干净目录完成；内部脚本通过不等于本项已完成。

1. 克隆仓库，使用 Node 22（项目 .nvmrc）和 npm，执行 npm ci、npm test。
2. 执行 npm run verify:package，确认 tarball 独立安装、包名导入和公共类型检查通过。
3. 执行 npm run demo:recovery 与 npm run demo:import，描述哪些步骤执行、哪些复用、哪些仍未知。
4. 用自己的最小 Project/Task 定义写一个独立消费者：注册、编辑、预检、模拟发布、关闭重开。
5. 注入丢失回执，确认恢复先核对，结果不明时后续步骤没有执行。
6. 记录运行时、操作系统、提交 SHA、接入耗时和阻塞点；不要提供密钥、真实账户数据或未脱敏数据库。

交付反馈至少包含：执行过的命令、预期与实际结果、最小合成复现、README 中不清楚的段落。
