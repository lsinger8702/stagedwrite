# Stripe Product update example

Updates the **same Product's name** with StagedWrite. No payments, subscriptions, Price replacement, or production keys. Unlike the older create sample, this is a separate adapter with confirmed values and update inspection.

## Offline, no credentials

```sh
npm ci
npm run demo:update
npm run verify:update
```

[HTML](../../docs/examples/update.html) · [ZIP](../../docs/examples/stagedwrite-update.zip). The trace is produced by the real library and SQLite against a mock Stripe-shaped transport. It covers create → publish → edit → preflight → update publish → injected receipt loss → reopen → resume → no-write publication. Mock clock/IDs are fixed only in this offline process; CI checks the generated bytes. **This is not a live Stripe update recording.**

## Sandbox

Configure STRIPE_SECRET_KEY (test secret/restricted key with Product read/write permission) and STRIPE_SANDBOX_ACCOUNT in a local ignored environment file. Never put keys in arguments, source, logs or reports.

```sh
npm run build
node --env-file=.env.stripe examples/stripe-update/run.mjs \
  --allow-test-writes --state-dir=.stripe-example/product-update
```

Creates one test Product and changes its name from A to B. The Product remains available for inspection; this example does not delete it. A [reviewed real sandbox recording](../../docs/examples/stripe-update-sandbox-result.json) covers this flow: initial publication, update receipt loss, SQLite reopen and same-Run recovery, then no-op publication. All seven HTTP responses were test-mode 200 responses; only one create POST and one update POST were sent.

Continue the same state directory after interruption:

```sh
node --env-file=.env.stripe examples/stripe-update/run.mjs \
  --allow-test-writes --state-dir=.stripe-example/product-update --resume
```

The driver preserves manifest, SQLite and raw traces locally. Source, key fingerprint and target must match. Do not replace the directory to retry an unresolved operation. The script never prints credentials. A full trace may include sandbox object IDs; do not publish it without reviewing/redacting it.

## Confirmation and recovery

`confirmed` comes from the actual successful Product response. Before deliberately losing an update receipt, this example atomically saves that response and the exact original request fingerprint in a local receipt journal. On reopen, reconcile can adopt that durable receipt without issuing another POST. This proves response-based recovery; it does **not** claim GET equality proves a particular request finished.

If the network fails after the effect but before the local journal is saved, there may be no conclusive evidence and the Run stays unknown. The sample does not replay a POST after an arbitrary delay or assume Stripe's idempotency storage is permanent. Preserve the journal with the SQLite file. A corrupted or lost journal is not proof of no effect.

Stripe Product updates here have no CAS token: **single writer only**. Do not change the same Product in Dashboard/another application during the run. Preflight/readback detects observed drift but cannot close the gap between a GET and the subsequent POST.

Official contracts: [Update a Product](https://docs.stripe.com/api/products/update), [API v1 idempotency](https://docs.stripe.com/api/idempotent_requests). Library behavior is independently covered by [the lifecycle tests](../../tests/update-lifecycle.test.ts).

## Recorded evidence

The raw local trace is intentionally not committed. After a successful live run, export an allowlisted summary with `node scripts/record-stripe-update.mjs <state-directory>`, review it, and update the reviewed-byte assertion in `evidence.test.mjs`. `npm run verify:update` checks both source and recording digests offline. Changing a digest is not a substitute for rerunning and reviewing the experiment. The HTML walkthrough remains a deterministic mock; the linked sandbox recording is separate evidence.
